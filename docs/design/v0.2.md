## Current state

These are the facts the design depends on.

- Six tools are registered: `agiw_readiness`, `agiw_status`, `agiw_consent`, `agiw_jev_pre`, `agiw_jev_post`, `agiw_nisi_run` (tools.py:33-116, 205-212). Every input schema is closed with `additionalProperties: false` (tools.py:14, 17, 21, 28, 62, 74, 86, 113).
- The server answers `initialize`, `ping`, `tools/list` and `tools/call` and nothing else (rpc.py:110-135). It declares only `tools` with `listChanged: false` (rpc.py:114). It sends no requests and no notifications to the client (rpc.py:90-92).
- `tools/call` accepts a `_meta` member and does not read it (rpc.py:128).
- One process handles one tool call at a time. Only `agiw_nisi_run` runs on a worker thread; everything else is answered on the main loop (rpc.py:277-287). All stdout writes happen on the main loop (rpc.py:207-210). The event queue between threads holds 16 entries and its `post` helper blocks while the queue is full (rpc.py:181, 186-192).
- Accepted protocol versions are `2025-11-25`, `2025-06-18`, `2025-03-26` and `2024-11-05` (rpc.py:26). The negotiated version is not stored after `initialize` (rpc.py:110-116).
- Consent is recorded when `consent.json` holds `schema` 1, `granted` true and the SHA-256 of the current disclosure (consent.py:90-93). The disclosure text includes the fixed questions (consent.py:49-64). The MCP tool refuses `grant` (tools.py:185-187). The CLI grant requires a terminal on stdin and the words "I agree" (`__main__.py`:40-54). Nothing checks who wrote the file: `_read` loads whatever JSON object is there (consent.py:75-87).
- The Jev tools check input bounds, then consent, then the key, then send one request (jev.py:85-110). The endpoint is a constant (consent.py:20, jev.py:30-32).
- `agiw_nisi_run` validates the ticket and the request, admits the ticket, runs, and releases the ticket (nisi.py:462-490). The run copies the verified vendored Nisi files and the host runner into a new temporary directory (nisi.py:514-527, 126-136), asks Node which permission flags it lists (nisi.py:201-231) and starts the runner (nisi.py:528-532).
- When `node --help` lists neither `--permission` nor `--experimental-permission`, `permission_flags` returns no flags and the label `none`, and the run proceeds (nisi.py:216-227). The result reports `sandbox: "none"` (nisi.py:589). One test asserts that result (tests/test_nisi.py:144).
- The Python syntax check runs the interpreter that runs agiw-mcp: the host passes `sys.executable` and its version (nisi.py:511-512), and the runner starts it with `-I -S -B` (nisi_runner.mjs:90-93). The result reports that interpreter's version (nisi.py:584). The input fingerprint leaves out the interpreter path and keeps its version (nisi_runner.mjs:263-264).
- The runner writes one JSON document to stdout when it finishes (nisi_runner.mjs:338-339, 350, 354). The host collects all of stdout and parses it after the process exits (nisi.py:343-420, 441-459). Runner stderr is drained and discarded (nisi.py:383).
- The vendored engine accepts only `adapters`, `candidate`, `candidateAuthorId`, `clock`, `reportStore` and `signal` as options (vendor/nisi/package/workflow/engine.mjs:162). It has no stage callback. The author, static check, test and reviewer adapters are built by the host runner (nisi_runner.mjs:272, 281-333).
- Jev calls are logged to `jev-activity.jsonl` with allowlisted, typed fields (activity.py:21-32, 35-56). Nisi runs have no per-call log (SECURITY.md:162).
- `config.json` is a closed set of ten keys (config.py:45-47). An unknown key is refused with `CONFIG_INVALID` (config.py:232-234). Five keys can also come from the environment (config.py:48-50). The environment also chooses which `config.json` is read: `AGIW_MCP_CONFIG_DIR`, when set, is the config directory (config.py:59-65); otherwise it is derived from `APPDATA` on Windows, `XDG_CONFIG_HOME` on other non-macOS systems, or the home directory (config.py:66-74). `config.json` and `consent.json` are both read from that directory (config.py:248, consent.py:72).
- Ticket admission is refused on Windows before the filesystem is touched (tickets.py:103-108, 666). Stale-lock recovery needs `fcntl`, which is absent there (tickets.py:83-86, 529-530).
- The vendored Nisi version is `0.2.0`, pinned by the manifest hash (nisi.py:40-41). The bundle may be updated only through AGIW Suite's `bundle_nisi.py`, which is not in this repository (AGENTS.md:127-130).
- CI checks a clone of AGIW Suite `main` against this checkout: LICENSE bytes, Suite's Nisi tree verified with this repository's pinned manifest hash, and the Jev model and endpoint in `JevKeychain.swift` (scripts/suite_compat.py:56-68, .github/workflows/ci.yml:197-212).

## Scope

### L1. Pin the consent disclosure hash

Any edit to `DISCLOSURE` or to the question text changes the disclosure hash, and every stored grant stops matching (consent.py:63-68, 90-93). That is the intended behavior when what is sent changes. It should not happen by accident. No test at this commit compares the hash with a fixed value: the tests call `consent.disclosure_sha256()` and never a literal (tests/test_keys_consent_config.py:134-163, tests/support.py:101).

Change: one test asserts that `consent.disclosure_sha256()` equals a literal. At this commit the value is `6ced7a609a6077f15e1aa3b1f31815225a451aa9c540848c5200e0188d3d1340` (computed in this lane with `PYTHONPATH=src python3 -B -c "from agiw_mcp import consent; print(consent.disclosure_sha256())"`). The test's failure message says that a deliberate change must update the literal and add a changelog line telling users to grant consent again.

Rule for the other lanes: none of them changes `DISCLOSURE`, `QUESTIONS`, `JEV_ENDPOINT`, `MAX_PRE_BYTES` or `MAX_POST_BYTES`. No existing grant is invalidated by this scope.

### L2. Refuse a Nisi run without a Node permission model

Today a Node whose help lists no permission flag runs the Nisi runner with no file-access limit, and the only signal is `sandbox: "none"` in the result (nisi.py:226-227, 589). SECURITY.md states this as a known limit and notes that no refusal code exists (SECURITY.md:96-101).

Change:

- New config key `allow_unsandboxed_nisi`, boolean, default `false`. Set only in `config.json`; no environment variable reads the key. The environment can still choose which `config.json` is read (config.py:59-74); see Threat model deltas.
- When the permission probe finds no flag and the key is false, `agiw_nisi_run` refuses with a new code, `NODE_SANDBOX_UNAVAILABLE`. The refusal happens after ticket admission and before the temporary directory is created. Today the probe runs after `mkdtemp` (nisi.py:514, 528). The `node --help` probe is split from building the per-directory flags, and the probe moves to just after `find_node` in `_run_validated` (nisi.py:493-496), ahead of `mkdtemp`. A ticketed run that is refused this way releases its ticket through the existing `finally` (nisi.py:487-490), as a `NODE_UNAVAILABLE` refusal does today (tests/test_tickets.py:702-710).
- Ordering is kept on purpose. Today admission comes before any Node process: `run` says so (nisi.py:465-466), README.md:280 and AGENTS.md:136 say overlapping scopes are refused before Node starts, and `find_node` runs only inside `_run_validated` (nisi.py:494), after `registry.admit` (nisi.py:486). The helpers at tests/test_tickets.py:618-634 fail a ticket refusal that calls `find_node`, `mkdtemp`, `subprocess.run` or `Popen`, and tests/test_tickets.py:611-616, 653-659 and 661-672 use them for `TICKET_REGISTRY_UNSAFE`, `TICKET_UNSUPPORTED_PLATFORM` and `TICKET_SCOPE_CONFLICT`. Moving the probe ahead of `registry.admit`, as an earlier draft of this document proposed, would change that ordering: a refused or overlapping ticket would first start `node --version` and `node --help`, `NODE_UNAVAILABLE` and `NODE_SANDBOX_UNAVAILABLE` would take precedence over admission refusals, those three texts would become false, and those tests would have to change. The cost of keeping the ordering is that a ticketed run refused by L2 creates its ticket lock file and removes it again before returning.
- With the key true, behavior is as today, including `sandbox: "none"`.
- `agiw_status` gains `node.sandbox`: `"node-permission"`, `"none"`, or `null` when Node is missing or the probe failed. `agiw_readiness` fails the existing `node` check, with a fix line, when the label is `none` and the key is false.
- A failed probe still refuses with `NODE_UNAVAILABLE` and is still not cached (nisi.py:211-213).

Unknown: whether any Node release at or above the minimum `22.0.0` (nisi.py:42) prints a help text with neither flag. This lane ran only `node --help` on Node 24.22.2, which lists `--permission`. If no supported Node lacks the flags, the refusal is reachable only with unusual builds, and the change is still correct.

This is a behavior change for anyone on such a Node. See Migration.

### L3. Select the Python interpreter for the syntax check

The Python syntax check uses the interpreter that runs agiw-mcp (README.md:276, nisi.py:511). The server needs Python 3.10 or newer (pyproject.toml:10). A candidate meant for an older Python is therefore compiled with a newer grammar and can pass with syntax its target does not accept. AGIW Suite's command-line package allows Python 3.9 (README.md:65).

Change:

- New config key `check_python`: an absolute path to a Python interpreter, or unset. Unset keeps today's behavior. Set only in `config.json`; no environment variable reads the key, and the environment can still choose which `config.json` is read (config.py:59-74). It is not a tool argument: `agiw_nisi_run` keeps refusing unknown arguments (tools.py:113, nisi.py:254-258).
- Validation at load: a string of 1 to 1024 characters, absolute, without NUL or control characters. Existence is not checked at load.
- At run time, after ticket admission and before the temporary directory is created (the same place as the L2 probe, so ticket refusals still come first), the host starts `<check_python> -I -S -B -c <fixed version script>` with the probe environment (nisi.py:151-166) and a 3 second limit, and accepts only output of the form `X.Y.Z`. Anything else refuses with a new code, `CHECK_PYTHON_UNAVAILABLE`. The message names the config key and not the path.
- The probed version replaces `sys.version` in the payload's `pythonVersion` and in the result's `pythonCheckerVersion` (nisi.py:512, 584). The path replaces `sys.executable` in `python` (nisi.py:511). The input fingerprint keeps its rule: version in, path out (nisi_runner.mjs:263-264).
- `agiw_status` shows the configured path through `display_path` and the probed version. `agiw_readiness` adds a check with id `syntax_python` after `nisi` only when the key is set. The id is not `check_python`, because readiness.py:28-31 already has a function `check_python()` whose check id is `python`.

Unknown: the oldest Python the fixed checker script (nisi_runner.mjs:25-36) runs under. It uses `compile`, `sys.stdin.buffer` and `%` formatting. The lane sets the floor from what CI can install and run, and states it.

Status: landed in #53. The server enforces no minimum version for the selected interpreter; AGENTS.md states that the checker is tested on Python 3.12 and newer.

### L4. Progress notifications for `agiw_nisi_run`

A Nisi run can take up to 1800 seconds plus a 30 second margin (tools.py:110, nisi.py:532), and the client hears nothing until the result.

Change:

- If a `tools/call` for `agiw_nisi_run` carries `params._meta.progressToken` as a string or an integer, the server sends `notifications/progress` for that token during the run. A boolean or any other type is treated as absent. Other tools ignore the token; they answer on the main loop without a worker (rpc.py:286-287).
- Events come from the host runner's own adapter wrappers (nisi_runner.mjs:272, 281-333). The vendored Nisi files are not touched.
- Runner to host: stdout becomes line-delimited JSON. Event lines have `kind: "agiw-mcp.nisi-event.v1"` and exactly `stage` (one of `author`, `static`, `tests`, `review`), `attempt` (integer) and `status` (`started` or `finished`). The last line is the existing `agiw-mcp.nisi-run.v1` document, unchanged (nisi.py:43). The host reads lines as they arrive, validates event lines against that allowlist the way `activity.py` validates its fields (activity.py:21-32), and drops anything that does not match. A runner that prints only the result line, such as the test fakes (tests/support.py:228), still works.
- Events carry no model text, task text, path or model id.
- Host to client: the worker hands each event to the main loop through the existing queue as a new event kind, so stdout stays single-writer (rpc.py:207-210). The hand-off does not block: if the queue is full the event is dropped. The existing `post` helper blocks (rpc.py:186-192) and is not used for this. The worker posts `done` after its last event, so no progress follows the result. No progress is sent once the request is cancelled (rpc.py:240-241, 263-264).
- Notification: `progress` is the event count so far, starting at 1 and increasing. `total` is omitted because the number of stages depends on repairs. `message` is `"<stage> attempt <n> <status>"` and is sent only when the negotiated protocol is `2025-03-26` or newer. `serve` starts storing the negotiated version for that purpose; today it does not (rpc.py:110-116).
- Limits: at most 64 events per run are forwarded. All stdout bytes, events included, still count against the 16 MiB cap (nisi.py:54, 362-365).
- No capability is added to `initialize`.

Not claimed: that any client shows these notifications, or that they extend a client's request timeout. No client is launched by this repository's tests (README.md:268). There is no heartbeat, so a long author call still produces no update between its `started` and `finished` events.

Status: landed in #56. Attempt numbers are the engine's zero-based attempt, and `finished` means the adapter call settled, not that the stage passed (see README.md).

### L5. A local record of Nisi runs

Change: `nisi-activity.jsonl` in the config directory, one line per `agiw_nisi_run` call that passes input validation, written the same way as the Jev log (activity.py:35-56): mode 0600 on creation, rotated to `.1` above 1 MiB, write failures never fail the tool. `activity.record` is generalized to take a file name and a field allowlist.

Fields: time, `outcome` (the report outcome or the refusal code), `inputFingerprint` or null, `candidateFingerprint` or null, `repairAttempts` or null, `sandbox`, `ticketed` (boolean), `nisiVersion`, `elapsedMs`. No task text, file content, path, ticket id, owner, model id or endpoint.

New config key `nisi_activity_log`, boolean. The default is an owner decision (D3 below).

Status: implemented with `nisi_activity_log` defaulting to false, because D3 is open and off is the safe default. D3 is not decided by this. The record has no reader: no tool and no CLI command shows it. `activity.record_nisi` is a second function beside `activity.record` and not a generalization of it, so the Jev log is untouched. A call refused before validation completes (invalid arguments, `TICKET_REQUIRED`) adds no line. The Nisi log is also opened without following a symlink and only as a regular file.

The Nisi writer serializes the size check, rotation and append with an exclusive
`nisi-activity.jsonl.lock`. Lock acquisition is bounded and skips the record on
contention; an interrupted owner can leave a lock requiring manual removal only
after all writers have stopped. There is no stale-lock reclamation. The size
check is repeated under the lock so concurrent rotations cannot replace the
retained backup with a freshly created file. A short write is rolled back before
releasing the lock. If rollback fails, the lock is retained so later calls skip
the damaged file; stop writers and inspect or remove that log before manually
removing the lock. Retention remains the current log plus one backup, and a
later ordinary rotation replaces that backup. Logging failures never change the
run result.

The writer also refuses hard-linked logs, refuses a symlinked config directory,
and preserves existing directory permissions. New files use mode 0600 on macOS
and Linux. Directory-relative operations anchor the writes on macOS and Linux. Platforms
without that support retain path checks with a check-to-use replacement race;
native Windows race behavior is not verified. The nullable
fields provide safe defaults for malformed report metadata: `repairAttempts`
must be an integer excluding booleans, from 0 through 1000; otherwise the record
uses null. `sandbox` must be `node-permission` or `none`; otherwise it uses null.
The report returned to the caller is unchanged by this normalization.

Caveat to document: `inputFingerprint` is a hash over the request (nisi_runner.mjs:263-264). Someone who can read the file and guess the exact inputs can confirm the guess. The Jev log's `inputSha256` has the same property (jev.py:86, activity.py:23).

### L6. Protocol `2026-07-28` gap list (read-only)

The server does not implement protocol `2026-07-28` (README.md:74, rpc.py:25). What that version requires of a stdio server with tools only is unknown here: this lane did not read that specification. L6 is a read-only lane that reads the published specification and writes a gap list under `docs/design/`. It changes no code and makes no commitment to implement.

## Non-goals

- A release, a tag, a version bump or a PyPI publication. Not decided.
- Granting consent through MCP, or any OS user-presence check for consent.
- Any change to what the Jev tools send, to the fixed questions, or to the endpoint. No automatic retry.
- New tools. Reading or writing project files. Executing generated code.
- A remote or HTTP MCP transport, OAuth, or sessions.
- Ticket admission on Windows. It needs reparse-point, ownership and ACL checks on the state directory and a replacement for `flock` in recovery (tickets.py:43-46, 103-108, 529-530). Killing the whole runner process tree on Windows timeouts is in the same group (nisi.py:333-340, SECURITY.md:110-111). Both need work and testing on Windows and are large enough for their own design.
- Updating the vendored Nisi. It goes through AGIW Suite's bundle script (AGENTS.md:127-130).
- Covering the host runner with a pinned hash. The runner is copied separately from the manifest-checked files (nisi.py:136, SECURITY.md:84-85). A hash stored in the same installed package would detect a damaged install and would not stop anyone who can edit the package.
- Moving private scrub definitions out of the scrub checker (roadmap.md:21). The roadmap says it needs an owner decision (roadmap.md:10).
- Ticket changes. A separate audit of `tickets.py` is planned; its findings are unknown at the time of writing and are not anticipated here.

## Threat model deltas

The baseline is the threat model in [SECURITY.md](../../SECURITY.md) (SECURITY.md:130-152).

**Consent: no change to the trust boundary.** The consent record is a JSON file in the config directory. Any process running as the same user that can write that directory can create, alter or forge it, and an assistant with shell or file access is such a process (SECURITY.md:54-57, 144). Which directory that is can be chosen through the server's launch environment (config.py:59-74; see the config paragraph below). This scope does not add a signature, a key or a user-presence check, and none is claimed. The MCP tool still cannot grant (tools.py:185-187). L1 only guards against an accidental change of the hash that grants are bound to.

**Config becomes slightly more powerful.** Two new keys relax or redirect behavior: `allow_unsandboxed_nisi` turns the L2 refusal off, and `check_python` names a program the runner will start. Both sit behind the same boundary as the consent record, and that boundary has two parts. One is same-user write access to the config directory. The other is the server's launch environment: `AGIW_MCP_CONFIG_DIR` selects the config directory outright (config.py:59-65), and `APPDATA`, `XDG_CONFIG_HOME` and the home directory decide it otherwise (config.py:66-74). Whoever sets that environment, for example in the `env` block of the client file that starts the server, which for Cursor can be a file inside the project (README.md:111, 204, 213), can point the server at a directory they control and so choose a `config.json` that sets either key, and a `consent.json`, without writing the user's config directory. An MCP tool caller cannot set either key, because neither is a tool argument and no environment variable reads either key, and a tool call cannot change the server's environment. A process that can write the config directory can already do more than either key allows. Mitigations for `check_python`: it is started with `-I -S -B`, a fixed script, the candidate on stdin, the minimal environment and a time limit, as the current interpreter is (nisi_runner.mjs:90-93). The path does not appear in refusals.

**The syntax-check interpreter is outside Node's permission model, as today.** The runner passes its own permission flags only to Node children (nisi_runner.mjs:24). The Python child is started without them (nisi_runner.mjs:92). L3 does not change that; it changes which binary it is.

**L2 removes a fail-open path.** After L2, the claim "a Nisi run cannot change files outside its temporary directory" (SECURITY.md:137) rests on Node's permission model by default, and no longer silently on nothing when the flags are missing. `--allow-child-process` is still set, and `--allow-net` when Node lists it (nisi.py:222-230); loopback is still enforced by URL validation and not by Node (SECURITY.md:116-118).

**L4 adds a server-to-client channel.** New risk: runner output reaching the client as notifications. Mitigation: events are validated against a closed set of enum and integer fields on the host, the `message` is composed by the host from those fields, and nothing else on an event line is forwarded. The count is capped. Stdout stays single-writer. Diagnostics still go to stderr without request content (rpc.py:44-49).

**L5 adds a local file.** It holds hashes and codes. See the caveat under L5. It is never sent anywhere.

**No new network destination.** Destinations stay as listed in SECURITY.md (SECURITY.md:11-16).

Out of scope, unchanged: a compromised local account, Node or Python installation, a malicious local model server, and what TypeSafe does with data (SECURITY.md:142-152).

## Compatibility

**AGIW Suite.** Suite does not start this server (README.md:65, scripts/suite_compat.py:8-9). The shared pieces are the Nisi v0.2.0 bytes, the LICENSE bytes and the Jev model and endpoint pin (scripts/suite_compat.py:56-68). This scope touches none of them, so the `suite-compat` CI job is unaffected.

One coupling to keep in view: `suite-compat` verifies Suite's `vendor/nisi` with this repository's pinned manifest hash (scripts/suite_compat.py:61, nisi.py:86-87). If Suite `main` moves to a different Nisi bundle, that job fails on every pull request here until this repository takes the same bundle. At Suite `origin/main` `0315afb` (the local clone's ref, which matched the remote `main` when this revision was written), Suite's `vendor/nisi/manifest.json` still says `0.2.0` and hashes to the value pinned at nisi.py:40. Whether and when Suite plans to change it is unknown.

**Nisi.** The runner calls the vendored `runWorkflow(task, { adapters })` (nisi_runner.mjs:334). L4 adds events in the host's adapter wrappers and passes no new option to the engine, which would refuse one (engine.mjs:162). Nothing in this scope depends on a newer Nisi. In the local Nisi clone used for this lane (`origin/main` at `dbd0d24`, not fetched by this lane) `package.json` says `0.3.1`, so the vendored bundle is behind the Nisi repository. The remote `main` has moved past `dbd0d24` since; that newer commit was not read. Whether a newer Nisi keeps the adapter contract the runner uses was not checked.

**MCP clients.** Tool names and schemas do not change, so the Inspector `tools/list` check in CI keeps its expected list (.github/workflows/ci.yml:167-170). A client that sends no progress token sees no new traffic. Behavior of specific clients with progress notifications is unknown.

**Platforms.** No change to supported platforms. On Windows, tickets stay refused. L3's probe must work with a Windows interpreter path; L2's label logic is already platform-neutral (nisi.py:228-231).

## Migration

- **Consent.** No change. Existing grants on current main stay valid. (A grant made under the `v0.1.0` tag was already invalidated by an earlier disclosure correction on main; CHANGELOG.md:54.)
- **Config.** Existing files keep working: the three keys are optional. A file that uses a new key is refused by any older build with `CONFIG_INVALID`, because the key set is closed (config.py:232-234). Anyone who installs an older revision again must remove the new keys first. The docs for each key say so.
- **L2 default.** A user whose Node lists no permission flag gets `NODE_SANDBOX_UNAVAILABLE` where a run used to proceed. The refusal names the two ways out: a Node that lists the flag, or `allow_unsandboxed_nisi: true`. The changelog entry is marked as a behavior change.
- **Runner protocol.** The runner and the host ship in the same package and the runner is copied fresh for each run (nisi.py:136), so there is no mixed-version case to handle.
- **Tickets.** No change to lock files or `identity.key`.
- **New file.** `nisi-activity.jsonl` appears in the config directory if L5 lands and is enabled. Deleting the config directory, as the uninstall section already describes (README.md:293), removes it.
- **Docs per lane.** README (configuration keys, limits, "Does not, yet"), SECURITY.md (Nisi runs, Local records, threat model) and AGENTS.md are updated in the lane that changes the behavior, in the same pull request. `roadmap.md` and `CHANGELOG.md` lines are proposed in each pull request body and applied by whoever lands it, to avoid conflicts between lanes.
