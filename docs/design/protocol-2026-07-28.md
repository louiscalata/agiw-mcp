# Protocol 2026-07-28 gap list for agiw-mcp

Status: G1 to G6, G10 and G13 are implemented in `rpc.py` as a dual-era server and pinned by `tests/test_rpc_modern.py`; every legacy frame and every legacy test is unchanged. The gap list below is otherwise kept as written on 2026-11-16 against `origin/main` at commit `9c0fff9`, when it was read-only, and every `file:line` reference to `rpc.py` is to that commit, not to current main. Entries not named above remain open.

## Answer in brief

- A revision dated `2026-07-28` exists and is published as the current revision. The versioning page names it as current. Its changelog is written against `2025-11-25`.
- agiw-mcp implements none of it. In that specification's own terms, agiw-mcp is a legacy server: it answers the `initialize` handshake and nothing in the modern per-request model.
- Per the specification's compatibility matrix, a dual-era client works against agiw-mcp today by probing `server/discover`, getting an error, and falling back to `initialize`. A client that supports only the modern revision does not work against it.
- Making agiw-mcp a modern server needs six required changes (G1 to G6 below), all in `rpc.py`. The server can stay dual-era (the specification allows it), which keeps every legacy client working and keeps the legacy frames byte-identical.
- Four points are not settled by the pages read. They are marked UNKNOWN and listed together at the end.

## Classes

- **required**: the specification puts a MUST on a server, and the requirement reaches a stdio server that offers tools. It binds only an implementation that claims `2026-07-28`.
- **required (met)**: same, and agiw-mcp already meets it.
- **optional**: SHOULD, MAY, or a design choice the specification leaves open.
- **not applicable**: the feature does not reach a stdio, tools-only server like this one.

## Current behavior, from a harness run

A throwaway script (in the session scratchpad, not in the repository) called `rpc.handle` with modern-shaped requests carrying `_meta` with `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities`:

| Request | Result today |
| - | - |
| `server/discover` | error `-32601` Method not found |
| `tools/list` with modern `_meta` | result with only `tools`: no `resultType`, no `ttlMs`, no `cacheScope` |
| `tools/list` with no `_meta` at all | the same result, served |
| `tools/list` with `protocolVersion` `1900-01-01` | the same result, served; no `-32022` |
| `tools/call` of an unknown tool | error `-32602` `Unknown tool: nope` |
| `tools/call` of `agiw_status` | result with `content`, `isError`, `structuredContent`; no `resultType` |
| `ping` with modern `_meta` | result `{}` |
| `initialize` requesting `2026-07-28` | result with `protocolVersion` `2025-11-25` |
| `subscriptions/listen` | error `-32601` Method not found |

No request needs `initialize` first (`handle` has no such gate, rpc.py:85-141). That is the "era-ambiguous method processed under legacy semantics" case the compatibility matrix describes for legacy servers.

## Gap list

Spec section names are the page headings. Test names marked "new" do not exist yet; the others are existing tests that already pin today's behavior and must stay green.

### Required for a modern server

**G1. Per-request metadata and its validation.**
Spec: `basic`, "`_meta`", "Per-request protocol fields". `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` are required on every request; a request missing either is malformed and the server MUST answer `-32602`. `clientInfo` is SHOULD on the client side.
Code: `tools/list` and `tools/call` accept `_meta` (rpc.py:127, 135) and never read it; only `progressToken` is read from it (rpc.py:186-190). `handle` has no era decision at all (rpc.py:85-141).
Class: required.
Pin (new): a modern request missing `protocolVersion` gets `-32602`; missing `clientCapabilities` gets `-32602`; a request with no `_meta` and a legacy-style `initialize` first still behaves as today.

**G2. Version check and `UnsupportedProtocolVersionError`.**
Spec: `basic/versioning`, "Protocol Version Negotiation"; `basic`, "Error Codes". A server MUST answer a version it does not support with code `-32022`, `data.supported` listing supported versions and `data.requested` the one asked for. The code is in the range reserved for the specification (`-32020` to `-32099`).
Code: none. The only version logic is `SUPPORTED_PROTOCOLS` and the fallback to the newest legacy version inside `initialize` (rpc.py:26-27, 113-114). The harness shows a `1900-01-01` request being served.
Class: required.
Pin (new): unsupported version returns `-32022` with `supported` and `requested`; `supported` contains `2026-07-28`. Existing: `test_unknown_protocol_version_gets_latest` (test_rpc.py:102) keeps pinning the legacy fallback for `initialize`.

**G3. `server/discover`.**
Spec: `server/discover`; `basic/versioning` ("Servers MUST implement `server/discover`"). Result carries `resultType: "complete"`, `supportedVersions`, `capabilities`, optional `instructions`, `_meta["io.modelcontextprotocol/serverInfo"]` (SHOULD), and the cache hints in G6.
Code: method falls through to `-32601` (rpc.py:141). The pieces to reuse already exist: `INSTRUCTIONS` (rpc.py:28-36), server name and version (rpc.py:20, 120), capability shape (rpc.py:119).
Class: required.
Pin (new): discover returns the fields above; `capabilities` has `tools` and nothing the server does not do; the result equals what `tools/list` implies. Existing: the CI Inspector `tools/list` check (.github/workflows/ci.yml, job `uv-git-install`) keeps the expected six tool names.

**G4. `resultType` on every result.**
Spec: `basic`, "ResultType"; changelog major change 8. Results MUST carry `resultType`; `"complete"` for ordinary results. Clients treat an absent value as `"complete"` for earlier-protocol servers.
Code: absent from `_ok` results for `ping` (rpc.py:125), `tools/list` (rpc.py:130) and `tools/call` (rpc.py:78-82). A test pins its absence from the legacy `initialize` result (test_rpc.py:89).
Class: required on the modern path only. Legacy frames must stay as they are.
Pin (new): every modern result has `resultType: "complete"`. Existing: `test_no_token_has_byte_identical_result_frames` (test_rpc_progress.py:171) and `test_accepted_legacy_versions_are_negotiated` (test_rpc.py:83) keep the legacy frames identical.

**G5. Dual-era routing and process era.**
Spec: `basic/versioning`, "Backward Compatibility with Initialization-Based Versions" and its compatibility matrix. A dual-era server MAY serve both eras; a request with modern `_meta` is served statelessly, an `initialize` request selects legacy semantics scoped to the stdio process.
Code: `initialize` is handled at rpc.py:112-123 and stores the version in a process-wide variable (rpc.py:207, 240-241). A modern path must not read that variable (see G10).
Class: required in practice. The specification lets a server drop `initialize` (MAY), but the repository says legacy clients are the supported ones (see "OpenCode" below), so the dual-era choice is the one that does not break them.
Pin (new): a process that has answered `initialize` still answers a modern request by modern rules, and the reverse; a modern-only first request never needs `initialize`.

**G6. Cache hints on `tools/list` and `server/discover`.**
Spec: `server/utilities/caching`, "Cacheable Results", "Time-to-Live (TTL) Field", "Cache Scope Field"; changelog minor change 5. Servers MUST include `ttlMs` (integer, `>= 0`) and `cacheScope` (`"public"` or `"private"`) on `resultType: "complete"` results of `server/discover` and `tools/list`. The specification gives lists of tools that are identical for all users as the example of `"public"`.
Code: `tools/list` returns `{"tools": TOOLS}` (rpc.py:130), the same constant for every caller. There is no per-user variation, so `"public"` is consistent with the code.
Class: required. The `ttlMs` value is a design choice (UNKNOWN 1).
Pin (new): both results carry both fields with valid types; `ttlMs` is not negative; the paginated-page scope rule is moot because `tools/list` is one page (rpc.py:127-129).

### Required, already met

**G7. stdio framing, stderr, shutdown.**
Spec: `basic/transports/stdio`. One message per line, no embedded newlines; nothing but MCP messages on stdout; stderr free for logs; the server SHOULD exit when stdin closes; the server MUST NOT write requests to stdout.
Code: `encode` writes ASCII JSON with a single trailing newline (rpc.py:158-169); diagnostics go to stderr (rpc.py:45-50); EOF ends the loop and joins the worker (rpc.py:300-301, 354-359); `respond` writes only replies and progress notifications (rpc.py:231-234, 288). Batches are rejected (rpc.py:87-88), consistent with "each message is a single request, notification, or response".
Class: required (met).
Pin: existing `test_stdio_subprocess_smoke` (test_rpc.py:173), `test_oversized_frame_is_discarded_and_stream_stays_aligned` (test_rpc.py:151).

**G8. Cancellation on stdio.**
Spec: `basic/patterns/cancellation`. On stdio the client MUST send `notifications/cancelled`; the server SHOULD stop and send no response; the server MUST NOT send `notifications/cancelled` except to end a subscription; races must be handled.
Code: rpc.py:309-329 sets the cancel flag for the active request and drops queued ones with the same id and type; rpc.py:290-292 suppresses the response of a cancelled run. The server never sends `notifications/cancelled`.
Class: required (met).
Pin: existing `test_cancelled_run_does_not_send_more_progress_or_a_result` (test_rpc_progress.py:240) and `test_progress_queued_before_cancellation_is_not_sent_after_it` (test_rpc_progress.py:253).

**G9. Progress notifications.**
Spec: `basic/patterns/progress`. Token in `_meta.progressToken`, string or integer; `progress` MUST increase; only for active requests; MUST stop after completion; `total` and `message` optional.
Code: rpc.py:186-197, 281-289. Count starts at 1, is monotonic, is capped (`nisi.MAX_PROGRESS_EVENTS`), and nothing is sent after cancellation or the result.
Class: required (met). The `message` field is gated by a string comparison against the negotiated legacy version (rpc.py:195); see G10.
Pin: existing `test_progress_is_monotonic_and_capped_at_64` (test_rpc_progress.py:216), `test_progress_after_result_is_ignored` (test_rpc_progress.py:230).

**G10. Statelessness.**
Spec: `basic`, "Statelessness". A server MUST NOT rely on prior requests on the connection for capabilities, protocol version, or client identity.
Code: the only protocol state in `serve` is `negotiated_version` (rpc.py:207, 240-241), read once, to decide whether a progress `message` is sent (rpc.py:195, 288). On a modern request that variable is `None`, so the `message` would silently be omitted; a modern path has to take the version from the request `_meta` instead. `tools/list` does not vary by connection (rpc.py:130). The pending queue and the active-run slot (rpc.py:205-206) order work inside the process; they are not conversation state.
Class: required for the modern path. The effect of the missing version on `message` is optional, since `message` is OPTIONAL in the specification.
Pin (new): a modern request with a progress token receives the `message` field without any prior `initialize`. Existing: `test_message_uses_the_negotiated_protocol` (test_rpc_progress.py:199).

**G11. Error codes.**
Spec: `basic`, "Error Codes"; `server/tools`, "Error Handling". Unknown tool is `-32602`. Implementations MUST NOT emit codes in `-32020` to `-32099` other than the three defined, and MUST NOT emit `-32002` or `-32042`.
Code: the file defines only `-32700`, `-32600` to `-32603` (rpc.py:38); an unknown tool is `-32602` (rpc.py:137-138); no `-32002`, `-32042` or `-3202x` appears under `src/agiw_mcp`. `Server busy` uses `-32603` (rpc.py:336). Adding G1 and G2 introduces `-32602` (already used) and `-32022` (defined).
Class: required (met); `-32021` (`MissingRequiredClientCapability`) is not applicable because no tool needs a client capability.
Pin: existing `test_error_codes` (test_rpc.py:107).

**G12. Tool definitions and results.**
Spec: `server/tools`, "Data Types", "Tool Result", "Error Handling". Valid `inputSchema` object; a no-parameter tool SHOULD use `{"type":"object","additionalProperties":false}`; a result with structured content SHOULD also carry the JSON as text; execution failures are results with `isError: true`.
Code: `_EMPTY` is `{"type":"object","properties":{},"additionalProperties":False}` (tools.py:15), which is valid and equivalent; tool names all match `[A-Za-z0-9_.-]{1,128}` (checked by script); `_tool_result` returns both text and `structuredContent` (rpc.py:78-82); tool failures are results (rpc.py:139-140). No `outputSchema` is published; it is optional.
Class: required (met).
Pin: existing `test_tool_errors_are_results_not_protocol_errors` (test_rpc.py:137).

### Optional

**G13. Result `_meta` server identity.**
Spec: `basic`, "Per-response protocol fields". Servers SHOULD put `io.modelcontextprotocol/serverInfo` in every result's `_meta`.
Code: server identity appears only in the legacy `initialize` result (rpc.py:120).
Class: optional. Adding it changes modern frames only.
Pin (new): modern results carry `_meta` `serverInfo` with name and version; legacy frames do not.

**G14. Deterministic tool order.**
Spec: `server/tools`, "Capabilities"; changelog minor change 3. Servers SHOULD return tools in a stable order.
Code: `TOOLS` is a module-level list (tools.py:54); the harness listed the six names in a fixed order.
Class: optional (met).
Pin (new): two `tools/list` calls return identical bytes of the `tools` array.

**G15. Removed methods and notifications.**
Spec: changelog major change 5 removes `ping`, `logging/setLevel`, `notifications/roots/list_changed`; major change 2 removes `initialize` and `notifications/initialized`.
Code: `ping` answers `{}` (rpc.py:124-125) and is kept responsive while a Nisi run is active (rpc.py:330-332); every notification is ignored without reply (rpc.py:103-104).
Class: optional. A dual-era server needs `ping` for legacy clients. The pages read do not say which error a modern server must return for `ping` (UNKNOWN 3). Ignoring unknown notifications is harmless.
Pin: existing `test_progress_arrives_before_result_and_ping_remains_responsive` (test_rpc_progress.py:129) stays for legacy.

**G16. `tools/list` pagination.**
Spec: `server/tools`, "Listing Tools" says the operation supports pagination and caching. The pagination page was not read.
Code: any `cursor` is rejected with `-32602` because all tools fit one page (rpc.py:127-129).
Class: optional. Whether rejecting a cursor on a single-page list is acceptable under the modern revision is not established here (NOT_READ).
Pin: existing `test_tools_list_rejects_a_cursor` (test_rpc.py:91).

## OpenCode

The repository says only this about OpenCode and the protocol: `README.md:91` and `AGENTS.md:123` state that protocol `2026-07-28` is not implemented and that OpenCode's default `legacy` handshake, through `2025-11-25`, is the one this server answers. `CHANGELOG.md:30` and `docs/release-notes/next.md:30` repeat that OpenCode protocol `2026-07-28` is not implemented. The repository does not say that OpenCode or any other client depends on a non-legacy handshake, and no test starts OpenCode (README.md:289). No such dependency is recorded here. Which handshake a given client version selects was not checked (NOT_RUN).

## Tests that would pin the work

New test module, for example `tests/test_rpc_modern.py`, using the `exchange` helper pattern of `tests/test_rpc.py`:

1. Missing `protocolVersion` and missing `clientCapabilities` each give `-32602` (G1).
2. Unsupported version gives `-32022` with `supported` and `requested` (G2).
3. `server/discover` result fields and `ttlMs`/`cacheScope` types (G3, G6).
4. Every modern result has `resultType: "complete"`; no legacy result does (G4).
5. An `initialize` earlier in the process does not change a modern request, and the reverse (G5, G10).
6. Modern `tools/list` has `ttlMs`, `cacheScope`, a stable order, and no `cursor` (G6, G14, G16).
7. Modern progress carries `message` without `initialize` (G10).
8. `_meta` `serverInfo` on modern results, absent on legacy (G13).
9. A modern `ping` expectation, once UNKNOWN 3 is settled (G15).

Existing tests that must stay green unchanged because the legacy path is kept: `test_rpc.py:53, 83, 91, 102, 107, 137, 173`; `test_rpc_progress.py:129, 171, 199, 216, 230, 240, 253`; the `scripts/stdio_handshake.py` check (it speaks `2025-03-26`) and the CI Inspector `tools/list` step.

`scripts/stdio_handshake.py` would gain a second, modern mode for `server/discover`; that is a script change in the implementing lane, not here.

## UNKNOWN: not settled by the pages read

1. The `ttlMs` value to publish. The specification fixes the field, not the number; the tool list is a constant for a given release.
2. Whether a server that declares no list-changed support must still accept `subscriptions/listen` (and acknowledge an empty set), or may answer it with `-32601`.
3. The exact error for a removed method (`ping`) sent with modern `_meta` to a dual-era server.
4. Whether `supportedVersions` in a dual-era `DiscoverResult` may list legacy versions. The `UnsupportedProtocolVersionError` example lists `2025-11-25` next to `2026-07-28`, but the discover page shows only a modern list.
